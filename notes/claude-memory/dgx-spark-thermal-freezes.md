The training box (spark-8d9d, DGX Spark GB10) hard-freezes under sustained GPU load. **Root cause is thermal, confirmed 2026-07-14.** Memory has nothing to do with it — do not re-diagnose it as memory.

**The evidence that settles it:** `torch.cuda.max_memory_allocated()` reports the arm0 run's peak CUDA usage as **1.40 GB out of 121 GB** (reserved 3.08 GB). That is the caching allocator's high-water mark, updated on *every* allocation — unlike 5 s `/proc/meminfo` polling, it physically cannot miss a transient spike. Both prior theories are dead: (a) sustained exhaustion — the pool's observed floor is 111 GB, and memguard's 90% trigger has never fired once; (b) a sub-second allocation spike hard-crashing before the kernel can log it — ruled out by the 1.40 GB high-water mark. Verified separately that `MemAvailable` *does* track CUDA allocations 1:1 on this unified box (allocated 20 GB → MemAvailable dropped 20.6 GB), so memwatch was never blind to GPU memory; `nvidia-smi` memory.used/total read `[N/A]` on GB10 and are useless.

**The actual mechanism:** under load the SoC package hits **95–97 °C** (`thermal_zone0`/`zone5`; idle is ~47 °C). `nvidia-smi -q` shows **`SW Thermal Slowdown: Active`** with both counters climbing live — SW Thermal Slowdown 95.8 s → 107.6 s and, critically, **HW Thermal Slowdown 38.5 s → 43.3 s**, the last-resort hardware protection. SM clocks throttle 3003 MHz (max) → 2463 → 2054. `fan.speed` reads `[N/A]`, so fan RPM can't be monitored from software. Because `watchdog: Hard watchdog permanently disabled` (NMI unsupported on aarch64), a thermal event the firmware can't handle gracefully takes the whole box down with no OOM entry, no Xid, and an empty `/sys/fs/pstore` — exactly the observed signature.

**Why `--workers 2` fixed it (and why the user's instinct was right for the wrong reason):** dataloader workers are separate processes pinning CPU cores on the *same package* as the GPU. The old hardcoded `num_workers=8` added 8 busy cores' worth of heat to a package already thermally saturated by a 96%-utilized GPU, pushing it past the lockup point. Cutting to 2 removed that headroom problem. The same fix (fewer workers + "low memory") cured a prior ich-maxvit run — the fix worked, but the mechanism was always thermal, which is why the memory tuning seemed to help and why chasing memory further is a dead end.

**GPU utilization is NOT the lever.** 82–96% util is the normal healthy band for this workload and the box ran there for many minutes without incident, so no threshold separates crash from no-crash — an "85% cap" does not fit the data. GB10 exposes no knob anyway: `power.limit`, `power.max_limit`, and Supported Clocks all read **N/A**, so `nvidia-smi -pl` and `-lgc` do not work. The real lever is heat.

**How to apply:** Keep `--workers 2` and `--gpu-mem-frac 0.67` in `~/sino_work/run_arm0.sh` (both added 2026-07-14). The memory cap costs nothing — steady state is 1.4 GB against an 82 GB ceiling so it never binds — and is worth keeping purely because it converts a hypothetical runaway allocation into a Python OOM traceback instead of a freeze (verified: a 106 GB request raises `OutOfMemoryError`, "81.53 GiB allowed"). **The open item is physical cooling** — at 95–97 °C with HW thermal slowdown actively firing, the box is surviving with no margin; check vents/dust/clearance/ambient before trusting long runs. Software mitigation added 2026-07-14: `train_twin.py` sleeps between epochs (`--cooldown 120`, on by default) and re-checks the hottest thermal zone against `--cool-target 70` °C, adding up to 10 extra 1-min waits before terminating cleanly (checkpoint saved, resumable). Temps land in `history.json` (`temp_pre/post_cooldown_c`, `cooldown_extra_min`). **Keep the cooldown at 120 s — decided 2026-07-14 with data, do not trim.** Observed: each ~80 s epoch heats ~59 °C → ~88-90 °C and recovers fully to idle in the 120 s pause; but throttle counters (`nvidia-smi -q`, Clocks Event Reasons Counters) still accrue ~4.7 s SW + ~0.55 s HW thermal slowdown per epoch minute near the peak, so a shorter pause = warmer epoch start = more HW-slowdown exposure, the exact mechanism behind the freezes. Throttle threshold: GB10 reports `GPU T.Limit Temp` as *headroom remaining* (throttles at 0), which lands at ~83 °C on the GPU sensor ≈ 95 °C SoC zones; throttling is clock-based (no watt cap exists or is settable on GB10). `~/.local/bin/memwatch.sh` now logs `gtemp=`/`soc=`/`sm=` every 5 s (that instrumentation is what caught this; it logged nothing but memory before). Related: [[arm0-training-recovery]], [[setup-vllm-nemotron]].

**SECOND FAILURE MODE — power-transient suspect (2026-07-15, three crashes in ~24 h):** ~06:35 (IDLE — arm3 had finished 04:51, nothing running), 20:40:21 (**~75 s into arm2 epoch 15**, right after the 120 s cooldown ended at 20:39:05), and 20:57:59 (**11 seconds after arm2 resumed** at 20:57:48, GPU load just ramping from a cool ~60 °C start). In every case the journal stops mid-line — no shutdown sequence, no panic, no OOM, zero kernel thermal/throttle/MCE/watchdog entries. **This is NOT the 2026-07-14 thermal mechanism:** every arm2 epoch peaked at only 85–88.7 °C (well under the 95–97 °C freeze zone), the cooldowns worked as designed, and an 11 s cold-start crash cannot be thermal. Two of three crashes at GPU-load onset + one at idle fits a **power-delivery transient** (voltage sag on GPU power ramp / marginal PSU-cable-outlet), which also explains why the user's dashboard showed crashes "during high utilization." sar note: training barely registers in sar (14.7% mem, load ~2.5/20 — GPU load is invisible there), so sar CANNOT distinguish idle from GPU-training; use the arms' train.log timestamps instead. Firmware current (EC `0x03000302`, `fwupdmgr` no pending updates). Next steps: swap power cable/outlet, bypass any strip/UPS; `startup-mem-watch.service` (installed 2026-07-15, enabled) runs `~/sino_work/boot_monitor/startup_mem_watch.sh` for the first 5 min of every boot with per-sample fsync; on-demand: `systemctl start startup-mem-watch` (needs polkit) or run the script directly.

**vLLM/ollama footnote:** neither is implicated. vLLM is NOT auto-started (manual via `~/start_nemotron.sh`; keep its cap at 0.70) and was not running for any captured crash. `ollama.service` was enabled at boot and was disabled+stopped 2026-07-14 (user does no local AI now); it was idle at ~30 MB and never a cause.

**Running sudo on this box:** there is NO passwordless sudo and NO askpass helper, and `sudo` fails from Claude Code's Bash tool *and* from the `!` prefix — both lack a TTY ("a terminal is required to read the password"). Use **`pkexec <cmd>`**: an active GUI session (seat0/tty2, `DISPLAY=:1`) makes polkit pop a graphical dialog the user approves. That is how ollama was disabled. Wrap in `timeout 60` so it can't hang if nobody is at the screen.
